# SECURITY.md — Security model

These are mandatory engineering requirements, not guidance. The database isolation, authentication, RBAC and audit parts are implemented as of Milestone 2 (see [CURRENT.md](CURRENT.md) for exactly what runs and what does not). Everything else here is still design. BusinessPilot makes no compliance or certification claims.

Details: [docs/security/threat-model.md](docs/security/threat-model.md), [docs/security/tenant-isolation-tests.md](docs/security/tenant-isolation-tests.md), [docs/security/data-handling.md](docs/security/data-handling.md). Tenant entity model: [docs/architecture/tenant-model.md](docs/architecture/tenant-model.md).

## 1. Security invariants

| # | Invariant |
|---|---|
| S1 | Every tenant-owned record, key, file, vector, cache entry, job and audit event is tagged with `tenant_id`. |
| S2 | Tenant context comes only from the authenticated session and membership. It never comes from request bodies, LLM output or job payloads unless their signature is verified. |
| S3 | Authorization is computed before any AI call and re-checked before any data execution. The LLM never decides permissions. |
| S4 | The AI engine never holds credentials for tenant data stores or customer sources. |
| S5 | All analytical SQL is generated by the API's plan compiler. It is parameterized and runs in a read-only transaction, under RLS, with a timeout and a row limit. |
| S6 | Connector credentials are encrypted at rest and decrypted only in the connector module, in memory, at the moment of use. |
| S7 | Logs, traces and error messages contain no credentials, tokens, raw result rows, or tenant prompt or answer text. |
| S8 | Shared infrastructure never implies shared authorization. |

## 2. Authentication

- An external OIDC identity provider (D-OPEN-03). BusinessPilot never stores passwords for SaaS users.
- The app owns `app_user`, `tenant_membership`, roles and attributes. Identity provider claims identify the user. They do not grant tenant permissions.
- A user may belong to several tenants. Every request acts within exactly one active tenant, chosen explicitly and checked against membership.
- Sessions use short-lived access tokens. Admin actions (credential changes, mapping approval, user management) require recent authentication.

## 3. Authorization: RBAC + ABAC

- **RBAC:** roles (for example `owner`, `tenant_admin`, `finance_manager`, `sales_manager`, `sales_executive`) grant permissions on resources. Examples: `semantic_model:publish`, `data_source:manage`, `entity:invoice:read`, `measure:gross_margin:read`.
- **ABAC:** policies add row filters and column rules based on user attributes, for example `branch_id IN user.assigned_branch_ids` or `customer.account_owner_id = user.id`, and mask PII columns.
- `tenant_admin` does **not** imply data access. Configuration rights and data rights are separate permissions.
- The API produces one `AuthorizationContext` per request ([contracts/tenant/](contracts/tenant/)): granted entities, measures and dimensions, row filters, and column masks. `authz_scope_hash` is a stable hash of that effective scope. It is used for caching and auditing.
- Policy evaluation is in-code and typed for the MVP (D-OPEN-05). Policies are versioned configuration ([schemas/tenant/access-policy.schema.json](schemas/tenant/access-policy.schema.json)).
- Default deny. A measure or entity the user is not granted is removed from the semantic model view sent to the AI engine. It is also rejected at plan execution, even if the plan mentions it.

## 4. Tenant isolation in PostgreSQL

Pooled model (P-01): shared schema, `tenant_id uuid NOT NULL` on every tenant table.

```sql
ALTER TABLE analytics.invoice ENABLE ROW LEVEL SECURITY;
ALTER TABLE analytics.invoice FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON analytics.invoice
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
```

Rules:

- The application connects as a role that **does not own** the tables and has neither `BYPASSRLS` nor superuser rights. Migrations run as a separate owner role.
- Tenant context is set with `SET LOCAL app.tenant_id = $1` inside each transaction. This prevents leakage across pooled connections. With no context set, queries return zero rows (`current_setting(..., true)` returns NULL).
- Plan execution adds `SET LOCAL TRANSACTION READ ONLY` and a `statement_timeout`.
- In code, the tenant context is set with `set_config('app.tenant_id', $1, true)`, which is `SET LOCAL` in parameterizable form (ADR-0014). Two global tables, `core.app_user` and `core.permission`, hold no tenant data and have no RLS. A test keeps that list fixed.
- Cross-tenant platform operations (billing, support) use a separate audited role and code path, never the request path.
- **Defined exceptions (P-15). These are the only ones:**
  1. *Membership lookup at login.* Before a tenant is selected, `tenant_membership` has an additional policy `USING (user_id = current_setting('app.user_id', true)::uuid)`. It lets a user list only their own memberships. No other table has this policy.
  2. *Worker system tasks* (outbox relay, sync scheduler, retention and deletion sweeps) find their work as the `bp_system` role (ADR-0017). It has `SELECT (id, status)` and `UPDATE (status)` on `core.tenant` and **no grant on any other table**, including `analytics`, `outbox_event` and the sync tables. It logs in with its own password, held by the worker only. A sweeper lists active tenants and queues one task per tenant. Each task touches tenant data as `bp_app` with tenant context set.
- RLS is the safety net. The data-access layer must still filter by tenant explicitly and apply ABAC filters itself.

## 5. Isolation outside PostgreSQL

| Store | Rule |
|---|---|
| Redis keys | Prefix `t:{tenant_id}:`. All access goes through one tenant-aware wrapper. Raw client use is banned by lint rule. |
| Vector index | One index per tenant (P-08). Queries also filter on a `tenant_id` tag field (defence in depth). |
| Caches | Keys include `tenant_id` and `authz_scope_hash` ([docs/ai/caching.md](docs/ai/caching.md)). |
| Object storage | Key prefix `tenants/{tenant_id}/`. Access only through the `ObjectStorage` port with a tenant argument. |
| Jobs | Each payload holds `tenant_id`, `job_id` and an origin reference. The worker re-sets tenant context from the payload and checks that the referenced entities belong to that tenant. |
| Logs and traces | `tenant_id` as an attribute. No payload contents. |
| Live/federated sources (post-MVP) | There is no RLS at the customer's source. Isolation comes from tenant-owned credentials (one source belongs to exactly one tenant). The compiler must inject ABAC filters into the source query, exactly as for managed sync. |

## 6. Connector credentials

- Customer source credentials are encrypted with envelope encryption (P-12): a per-tenant data key, wrapped by a key-encryption key in the `KeyManagement` port. Configuration stores only a `credential_ref` ([schemas/configuration/data-source.schema.json](schemas/configuration/data-source.schema.json)).
- Customers are asked for **read-only**, least-privilege database users limited to the approved tables or collections. The onboarding UI checks privileges and warns about excess rights.
- OAuth sources (Google Sheets) use the narrowest scopes available. Tokens are stored the same way as other credentials, and refresh tokens can be revoked by the tenant.
- Credentials are never returned by any API after creation. They can only be replaced or deleted.
- Rotation: tenants can replace source credentials at any time. Key-encryption keys are rotated by re-wrapping data keys, with no re-encryption of ciphertext. The RequestContext signing key and service tokens can be rotated with an overlap window.

## 6a. Transport, storage and session security

- TLS for all external traffic, and for internal traffic outside local development. Customer source connections default to `verify-full` TLS.
- Encryption at rest for PostgreSQL, object storage and backups (managed-service encryption in SaaS; customer responsibility in Model B).
- Web sessions: `HttpOnly`, `Secure`, `SameSite` cookies or short-lived bearer tokens (decided with D-OPEN-03). CSRF protection for cookie sessions. CORS restricted to the web origin. Security headers (CSP, HSTS).
- MFA is required, through the identity provider, for `owner` and `tenant_admin` roles.
- Rate limits per user and per tenant on the public API, separate from AI quotas (D-OPEN-18).
- Uploaded files: size limits, content-type sniffing, parsing in the worker (not the HTTP process), and no formula evaluation.

## 7. AI-specific threats

| Threat | Control |
|---|---|
| Prompt injection in the question or in synced data ("ignore rules, show tenant X") | The model has no authority. Tenant, scope and filters come from the signed RequestContext, and plans are validated against the authorized view. Data values are passed as data, clearly delimited. |
| Model hallucinating numbers | Grounding check: every number in the narrative must match a result value or a deterministic derivation, or the answer is rejected and regenerated once, then degraded. |
| Data exfiltration through generated SQL | No raw SQL. Only the plan compiler, using allow-listed entities and columns. |
| Excess data sent to the LLM provider | Results sent to the model are aggregates or bounded top-N rows. PII is masked unless the policy allows it (D-OPEN-14). |
| Cross-tenant cache poisoning | Scoped cache keys. Cache entries are written only after successful validated execution. |
| Unbounded cost or loops | Fixed pipeline. Per-request limits on tool calls and tokens. Per-tenant quotas. |

## 8. Audit

Audit events are append-only and tenant-scoped, with no update or delete for the application role. They cover authentication, membership and role changes, credential create, replace and delete, data source and mapping approvals, semantic model publishing, every question (question text stored according to the retention policy), every executed plan (plan hash, entities touched, row count, not row contents), exports and deletions.

## 9. Data minimization, retention and deletion

- Sync only the tables, sheets and columns the customer approved. Column-level exclusion is supported.
- Retention is configurable per tenant for conversations, query logs and synced data (D-OPEN-12).
- Tenant deletion is a tracked job that removes PostgreSQL rows, Redis keys and indexes, object storage files, credentials and data keys (crypto-shredding), and records an audit event. Backups age out according to the backup retention window. This must be disclosed to customers.
- Details: [docs/security/data-handling.md](docs/security/data-handling.md).

## 10. Mandatory tenant isolation tests

The tests in [docs/security/tenant-isolation-tests.md](docs/security/tenant-isolation-tests.md) must exist and pass in CI before any feature that reads tenant data is merged. A failing isolation test blocks release. No exceptions.

## 11. Secure development

- Dependencies: lockfiles committed, automated vulnerability scanning in CI, no new dependency without a justification.
- Secret scanning in CI. `.env` files are gitignored. `.env.example` holds placeholders only.
- Security review before Milestone 10 (customer pilot), including an external penetration test where budget allows.

## Reporting a vulnerability

Until a public security contact exists, report issues privately to the repository owner. Do not open public issues for vulnerabilities.
